## 2. Непреложные правила

Наследуются из `prototypes/a/CONCEPT-A.md`, раздел 2. Нарушать нельзя.

| Правило | Почему |
|---|---|
| Анимируем только `transform` и `opacity` | Нет перерасчёта layout, нет CLS |
| Скролл нативный, без scroll-jacking | Core Web Vitals (INP, CLS) из ТЗ 3.2, доступность, трекпады |
| Весь контент — в HTML, не в картинках и не в JS | Индексация Яндексом |
| Движение по токенам: `cubic-bezier(.2,0,0,1)`, сдвиг 16px, без пружин | Дизайн-система, раздел «Движение» |
| `prefers-reduced-motion` → статика | Доступность |
| Мобайл (<1024px) → без закреплений и без параллакса | Производительность |
| Страница остаётся читаемой без GSAP | См. фолбэк в `index.html:637-642` |

## 5. Подиум

Референс внешнего вида — нижняя треть `assets/podium.jpg`: тёмная эллиптическая плита
в перспективе, синий кант по верхнему ребру, свечение, мягкое отражение под плитой.

Собирается на CSS, растр не используется. Причина: кольца свечения под роботами должны
реагировать на ховер вместе с роботом, а запечённые в картинку кольца этого не умеют.

Ориентиры (числа уточнены после этапа A, см. §16.1 — исходные давали плиту вровень с роботами):
- Плита шире окна (`118vw`), чтобы срезанные торцы уходили за край, а не заканчивались в кадре.
- Вся геометрия сцены считается от одной величины `--robot-base` — высоты самого высокого
  робота. Пропорции сняты с эталона `assets/podium.jpg`:
  `--plate-h: calc(var(--robot-base) * .30)` — торец;
  `--plate-ellipse: calc(var(--robot-base) * .26)` — вертикальный размер верхней грани;
  `--plate-bottom: calc(var(--robot-base) * .16)` — зазор под плитой под отражение;
  `--feet: calc(var(--robot-base) * .40)` — линия ног от низа сцены;
  `--scene-h: calc(var(--robot-base) * 1.46)` — высота сцены, резервируется заранее.
- Верхняя грань — эллипс: отдельный слой с `border-radius: 50%`, залитый `var(--stage)`
  с лёгким радиальным высветлением к центру.
- Торец — слой ниже, `border-radius: 0 0 50% 50% / 0 0 100% 100%`, вертикальный градиент
  от `var(--stage-raised)` к `var(--stage)`.
- Кант и свечение — токен `--glow-edge`, он уже описывает ровно этот эффект:
  `inset 0 1px 0 #2f3bff80, 0 16px 48px -16px #2f3bffb3, 0 2px 0 -1px #2f3bff`.
- Отражение — мягкий градиент под плитой, затухающий в `var(--surface)`. Зеркальные копии
  роботов не делать: дорого по рендеру и на 2× ассетах даст мыло.

**Запасной вариант, если CSS-перспектива не даётся за разумное время:** вырезать нижнюю
полосу из `podium.jpg` (примерно `y 410-710`) и заретушировать чипы брендов и кольца.
Это допустимо, но хуже: теряется реакция колец на ховер. Сначала пробовать CSS.

### Кольца свечения

Под каждым роботом — `radial-gradient` эллипсом в `--lime` с низкой альфой.
Базовое состояние приглушённое, активное — ярче и шире. Анимируется `opacity` и `transform: scale`,
не `width`/`height`.

## 6. Роботы: размеры и позиции

Каждый робот — `<button class="robot">`, не `<div>`. Причины: клавиатурная навигация,
`:focus-visible`, семантика интерактивного элемента. Внутри — `<img>` с осмысленным `alt`
(категория + тип техники), `.robot-glow` и `.robot-label`.

### Масштаб

Из генерации масштаб не приходит и приходить не должен — каждый робот заполняет свой кадр.
Ставится вручную. Буквальные реальные габариты использовать **нельзя**: дрон высотой 0.8 м
рядом со стеллажом 2 м превратится в точку. Шкала сжатая.

Целевая высота на экране, в процентах от самого высокого:

| Робот | Реальная высота | Высота в сцене | Примечание |
|---|---|---|---|
| `robot-amr` | ~2.0 м | 100% | самый высокий, задаёт потолок |
| `robot-demolition` | ~1.6 м | 88% | |
| `robot-manipulator` | ~1.4 м | 82% | |
| `robot-cleaning` | ~1.3 м | 74% | |
| `robot-wellness` | ~1.3 м | 72% | |
| `robot-agro` | ~0.8 м | 62% | самый широкий — по ширине будет доминировать |

Числа — стартовая точка, доводятся на глаз. Критерий: ряд читается как парк техники,
ни один робот не выглядит игрушкой и ни один не подавляет остальных.

### Позиционирование

- Порядок слева направо: агро · стройка · уборка · производство · склад · велнес.
  Тот же, что на `podium.jpg`, чтобы сравнение со старой сценой было честным.
- Роботы стоят на верхней грани плиты: низ картинки касается эллипса, а не висит над ним.
  У эллипса в перспективе край ближе к центру ниже, чем по краям — учесть, иначе крайние
  роботы «утонут», а центральные «взлетят».
- Высота контейнера сцены фиксируется заранее, чтобы при загрузке картинок не было сдвига (CLS 0).

## 7. Три режима движения

Общее для всех трёх: микрожизнь (§8.1) и реакция на ховер (§8.2) работают всегда.
Режимы отличаются только тем, что происходит **без участия пользователя**.

### 7.1. Режим A — «Спотлайт» (по умолчанию)

Подиум статичен, все шесть стоят на местах. Раз в 4.2 с один выходит вперёд.

Активный робот:
- `y: -18, scale: 1.06`, длительность 0.7, `EASE`
- кольцо под ним ярче и шире
- его `.robot-label` получает полную контрастность

Остальные:
- `opacity: .62` (правка после этапа A, см. §16.4 — исходные `.42` стирали технику)
- **`grayscale` не делаем.** `filter` — это не `transform`/`opacity`, а серая копия вторым
  слоем стоит шести лишних картинок. Ограничиваемся прозрачностью, §2 это предпочитает.

Панель `.scene-caption` рядом с H1 подменяет текст на данные активного робота (§10).
Смена текста — кроссфейд, не мгновенная подмена.

Перехват: `pointerenter` на роботе останавливает автоцикл и делает активным его.
`pointerleave` возобновляет автоцикл через 1.5 с. Цикл продолжается с того робота, на который наводили.

Смысл режима: герой рассказывает шесть историй вместо одного плаката. Для b2b это ценнее
карусели, поэтому режим стоит по умолчанию.

### 7.2. Режим B — «Конвейер»

Плита — лента. Роботы едут справа налево, уходят за край экрана и заезжают снова.

- Трек дублируется ×2, анимируется `translateX` от `0` до `-50%` ширины трека,
  `ease: 'none'`, `repeat: -1`. Полный цикл ~48 с.
- Края экрана подрезают роботов: `overflow: hidden` на обёртке сцены. Сама плита
  при этом видна во всю ширину.
- `pointerenter` → лента плавно тормозит: `gsap.to(tl, { timeScale: 0, duration: .4 })`,
  робот поднимается. `pointerleave` → `timeScale: 1` за 0.6 с. Резкой остановки быть не должно.
- Панели `.scene-caption` в этом режиме нет — текст, привязанный к едущему объекту, не читается.

Смысл режима: прямое продолжение метафоры «линия сборки» из концепции A. Читается как поток
техники, но теряет ощущение выстроенного парка, ради которого сцена и рисовалась.

### 7.3. Режим C — «Только ховер»

Ряд статичен, автоцикла нет, ленты нет. Работают микрожизнь и ховер.

Это не «режим для сравнения ради галочки»: он же служит фолбэком для `prefers-reduced-motion`
(без микрожизни) и для мобайла (без ховера). Собрать его надо всерьёз.

### 7.4. Переключатель

Фиксированная панель в правом верхнем углу, три радиокнопки, выбор запоминается в `localStorage`.
Панель помечена как элемент песочницы — в продакшен не едет. Переключение режима
пересобирает таймлайны без перезагрузки страницы.

## 8. Общее поведение

### 8.1. Микрожизнь

У каждого робота бесконечный `yoyo`-твин по `y`. Длительности намеренно несоизмеримы,
чтобы роботы никогда не синхронизировались: 3.1 / 3.7 / 4.3 / 4.9 / 5.3 / 5.9 с.

Амплитуды разные по смыслу техники:
- `robot-agro` — самая заметная, ±6px плюс `rotation: ±0.4deg`. Он летает, ему положено.
- `robot-wellness` — самая тихая, ±2px. Кресло стоит на полу.
- Остальные — ±3px.

### 8.2. Ховер и фокус

`pointerenter` и `focus` дают одно и то же состояние:
- `y: -12, scale: 1.05`, длительность 0.24 (`--base`), `EASE`
- кольцо ярче
- подпись контрастнее
- остальные роботы приглушаются до `opacity: .68` (см. §16.4)

`:focus-visible` обязан давать видимое кольцо фокуса по правилу из `index.html:53`.
Ховер без клавиатурного эквивалента не принимается.

### 8.3. Параллакс от курсора

`pointermove` по герою сдвигает роботов с разными коэффициентами глубины:
от `0.008` у дальних до `0.022` у ближних. Использовать `gsap.quickTo`, не `gsap.to` на каждое
событие. Отключается на тач-устройствах и при `reduced-motion`.

### 8.4. Скролл-скраб

В `index.html:761-764` уже есть таймлайн: герой наезжает `scale: 1.18` и гаснет.
Послойная сцена делает это объёмным почти бесплатно — передние роботы уезжают быстрее задних.
Воспроизвести ту же механику, добавив разные коэффициенты по слоям.

## 9. Логобар

По ТЗ (стр. 384) логотипы производителей — **отдельный блок с подписью**
«Работаем с ведущими мировыми производителями», а не плинтус под роботами.
На старом растре они запечены в торец плиты — это надо развести.

Причина не только формальная: роботы на сцене идут по отраслям, а бренды с этими отраслями
не совпадают. Агродроны — это DJI и XAG, демонтаж — Brokk, и ни один из них в список семи
не входит. Плинтус создаёт ложное впечатление, что вот эти бренды делают вот этих роботов.

Состав по ТЗ: PUDU, GAUSIUM, KEENON, HIKROBOT, FORWARDX, UNITREE, ORIONSTAR, ссылка «и другие».

**Обновление:** заглушки заменены официальными логотипами в `assets/brands/` (старая папка
`homepage/logos/` удалена). GAUSIUM в наборе нет — его нужно найти отдельно.

Поэтому: сверстать логобар на том, что есть, с нормализацией по оптической высоте
(не по высоте бокса — логотипы придут с разными пропорциями и полями). Подмена файлов
не должна требовать правок вёрстки.

## 11. Доступность и адаптив

### `prefers-reduced-motion: reduce`
Режим C без микрожизни. Статичный ряд, ховер работает, автоцикла, ленты, параллакса
и скролл-скраба нет. Повторяет логику `index.html:369-373` и `index.html:757`.

### <1024px
- Только режим C. Автоцикл и лента отключены: ховера нет, а постоянное движение
  на телефоне жрёт батарею.
- Параллакса нет.
- Шесть роботов в ряд не помещаются. Варианты на выбор реализующего, с обоснованием в коде:
  либо горизонтальный `scroll-snap` по роботам, либо показ трёх с остальными за кадром.
- Подписи категорий остаются в DOM в любом случае — они нужны индексации.
- Свой кегль H1 и гаттер 20px: нижняя граница `clamp(40px, …)` из `styles.css` не помещается
  в 375px, «Роботизация,» занимает там около 270px. См. §16.8.
- Панель `.scene-caption` прячется вместе с автоциклом: без цикла она застывает на случайном
  роботе и врёт.

### Клавиатура
Tab проходит по шести роботам по порядку. Фокус даёт то же состояние, что ховер.
Enter/Space — заглушка (в продакшене уведёт на страницу отрасли).

### Без GSAP
Если CDN недоступен — ряд виден статично, подписи на месте, ничего не скрыто.
Механика фолбэка уже есть в `index.html:637-642`, переиспользовать её.

## 12. Производительность

- Вес ассетов героя ≤ 550 КБ. Сейчас шесть WebP дают 488 КБ — запас есть, но не большой.
- `fetchpriority="high"` только на два-три центральных робота.
- **`decoding="sync"` на всех шести.** Исходное требование `decoding="async"` отменено
  по итогам этапа A: см. §16.3.
- `will-change: transform` на роботах — и снимать после завершения въезда, иначе шесть
  постоянных композитных слоёв.
- Ленту и автоцикл ставить на паузу, когда герой вне вьюпорта (`ScrollTrigger` с
  `onEnter`/`onLeave`, либо `IntersectionObserver`).
- LCP не должен деградировать: крупнейший элемент — H1, а не картинка. Проверить, что
  сцена его не перебила.

## 13. Критерии приёмки

1. Три режима переключаются без перезагрузки, выбор переживает обновление страницы.
2. CLS = 0. Высота сцены зарезервирована, при загрузке картинок ничего не прыгает.
3. В анимациях только `transform` и `opacity`. `filter`, `width`, `height`, `top`/`left`
   в твинах отсутствуют.
4. 60 fps в простое на десктопе. Длинных задач >50 мс во время идл-анимации нет.
5. `prefers-reduced-motion` даёт статику — проверено переключением в системных настройках.
6. Клавиатурный проход по шести роботам работает, фокус виден, состояние то же что при ховере.
7. При отключённом JS или недоступном CDN ряд виден, подписи читаются.
8. На 375px ширины ничего не выезжает за экран и не появляется горизонтальный скролл.
9. Суммарный вес ассетов героя ≤ 550 КБ.
10. Подписи категорий и логобар присутствуют в HTML текстом, не картинкой.

## 14. Что не делать

- **Не трогать `index.html`.** Песочница отдельная. Перенос — после выбора режима.
- **Не делать классический слайдер** «один робот крупно + стрелки». Он убивает эффект парка
  техники, ради которого сцена и рисовалась. Три режима в §7 — исчерпывающий список.
- **Не делать настоящий 3D-поворот подиума.** Ассеты — плоские 2D-вырезы с фиксированного
  ракурса; при повороте на «заднюю» позицию перспектива развалится.
- **Не подключать Rive, Lottie, three.js, Spline.** Для b2b-лендинга не окупается, а LCP
  и мобильный перф испортит.
- **Не переносить в песочницу остальные секции главной.** Задача про движение сцены.
- **Не выдумывать цифры** для агро и велнеса (§10).

## 16. Уроки этапа A

Раздел дописан после сборки режима A. Всё перечисленное уже стоило времени один раз —
в режимах B и C повторять не надо. Ссылки на строки — `prototypes/motion/index.html`.

### 16.1. Пропорции подиума задаются от эталона, а не на глаз

На `assets/podium.jpg` роботы выше всей видимой плиты примерно в **2,3 раза**, а эллипс
верхней грани очень плоский — его вертикальный размер около **6% ширины плиты**. Первая
сборка держала плиту почти вровень с роботами: сцена читалась как тёмная полоса внизу
экрана, а не как подиум. Числа в §5 приведены к эталону, менять их вслепую не надо.

### 16.2. Потолок `--robot-base` задают две рамки, и обе обязательны

`--robot-base: min(300px, 30vh, 16vw)`.

- **По ширине:** сумма ширин шести роботов равна `5.03 × --robot-base` (посчитано по
  пропорциям ассетов). При 16vw ряд влезает в окно без обрезки крайних.
- **По высоте:** герой целиком обязан влезать в первый экран вместе с H1, лидом и кнопками.
  При 30vh на окне 1312×734 герой занимает 711px из 734. Если убрать эту рамку, низ плиты
  и отражение срезаются сгибом, и сцена выглядит недорисованной.

### 16.3. `decoding="async"` на крупных WebP роняет роботов из кадра

Симптом: от кадра к кадру пропадают разные роботы — то агро и склад, то стройка. В DOM они
при этом на месте, `naturalWidth` правильный, `opacity` единица, `elementFromPoint` возвращает
саму картинку. Причина — кадр уходит в композитор раньше, чем картинка декодирована.
Лечится `decoding="sync"` на всех шести. Требование §12 про `async` отменено.

Побочный вывод для отладки: **скриншот врёт**. Прежде чем чинить «пропавший» элемент,
надо проверить его через DOM — размеры, прозрачность, цепочку трансформаций предков.

### 16.4. `opacity: .42` рассчитан на тёмный фон

Страница светлая (`--surface: #f3f2ef`), техника белая. На `.42` неактивные роботы исчезают
целиком, и сцена выглядит так, будто картинки не загрузились. Рабочие значения: **.62**
для спотлайта, **.68** для ховера. Основную разницу между активным и остальными держат
подъём, масштаб и яркость кольца, прозрачность только помогает.

### 16.5. Кольцо свечения — это след на плите, а не обруч вокруг робота

Два отдельных промаха первой сборки:

- **Ширина.** Кольцо во всю ширину картинки читается как самостоятельный обруч и цепляется
  за соседние. Рабочее — около **60% ширины картинки** (`left: 20%; right: 20%`).
- **Вертикаль.** Центр кольца обязан лежать **на линии ног**, то есть `bottom` равен минус
  половине высоты кольца. Иначе кольцо висит отдельно от робота.
- **Заливка.** Залитый лаймовый эллипс выглядит как трава под техникой. Нужен мягкий контур:
  `radial-gradient(closest-side, …)` с прозрачной серединой.

### 16.6. Подписи категорий лежат на одной горизонтали

Роботы подняты на разную высоту (`--lf`), чтобы повторить кривизну эллипса. Если подпись
позиционировать от низа робота, подписи идут лесенкой и ряд выглядит кривым. Подъём надо
вычитать: `bottom: calc(… - var(--robot-base) * var(--lf, 0))`.

### 16.7. Плита — один слой, а не слоёный пирог

Синяя кромка отдельным элементом поверх торца даёт **две дуги**: у слоёв разной высоты
`border-radius` в процентах расходится по краям. Кромка — это `border-bottom` самого торца.

Там же: размытый ореол из токена `--glow-edge` (`0 16px 48px -16px #2f3bffb3`) нельзя вешать
на эллипс верхней грани — он затягивает синевой весь низ экрана. На эллипсе оставлены только
«жёсткие» части токена, ореол перенесён на торец и ослаблен.

### 16.8. Мобайл наследует кегль, который в него не помещается

H1 в `styles.css` — `clamp(40px, 5.2vw, 80px)`. Нижняя граница 40px не влезает в 375px.
На мобайле нужен свой кегль (`clamp(30px, 8.6vw, 44px)`) и гаттер 20px вместо 40px.

### 16.9. Слои трансформаций разведены по одному на механику

Четыре вложенных слоя на каждого робота, и это не украшательство: два твина на одном `y`
дерутся и дают дрожь.

```
button.robot      параллакс от курсора (x, y) — gsap.quickTo
  .robot-depth    скролл-скраб, свой коэффициент глубины
    .robot-life   микрожизнь, бесконечный yoyo
      .robot-fig  ховер и спотлайт (y, scale)
        .robot-glow + img
```

Подпись `.robot-label` висит на самой кнопке, вне этих слоёв, — её не должно таскать
микрожизнью.

### 16.10. Первый `applyMode` не должен красить сцену

`paint()` ставит твины с `overwrite: 'auto'`. Вызванный на старте, он затирает `gsap.from`
въезда, и сцена появляется рывком. Первый вызов идёт с флагом `initial`, а запуск автоцикла
откладывается на время въезда.

### 16.11. Панель песочницы обязана сворачиваться

Развёрнутая панель в правом верхнем углу (§7.4) закрывает карточку метрик и панель результата,
то есть ровно то, что оценивают. Сделана как `<details>`, свёрнутое состояние по умолчанию
и запоминается в `localStorage`.

### 16.12. Чем проверять

- **Живой Chrome обязателен.** Headless-кадр не показал ни срезанный сгибом низ сцены,
  ни выпадающих роботов.
- **Headless на macOS не отдаёт окно уже 500px.** Запрошенные 375 рендерятся как 500,
  а кадр обрезается до 375 — и вёрстка выглядит «поехавшей», хотя с ней всё в порядке.
  Настоящие 375 проверяются через iframe шириной 375 внутри страницы-обёртки.
- **Не «замораживать» сцену через kill всех твинов** ради чистого кадра: это гасит
  незавершённый `gsap.from` въезда и стирает половину героя. Проще дождаться нужного кадра.
